# Z9★ 온라인 매크로

`Z9★ 온라인`(내 맘대로 Z9별) 창을 대상으로 키·마우스 입력을 자동화하는 도구.
외부 패키지 없이 파이썬 표준 라이브러리와 `ctypes`로 Win32 API를 직접 호출한다.

---

## ⚠ 먼저 알아둘 것

**매크로 사용은 이 게임의 운영정책 위반이며, 실제 제재 사례가 있다.**
2021년 7월 자동 사냥 프로그램 적발로 생활기술 경험치가 초기화되어 레벨 210 →
레벨 1로 강등된 사례가 기록되어 있다(이후 복구됨). 이 도구는 탐지를 회피하는
기능을 포함하지 않으며, 사용에 따른 계정 제재 위험은 사용자 본인이 진다.

## 실행

```
dist\Z9매크로.exe      ← 만들어 둔 실행 파일 (버전 1.0)
```

실행하면 관리자 권한을 묻는다. 허용해야 입력이 게임에 들어간다 (아래 참고).

소스에서 바로 돌리려면:

```
관리자로 실행.bat
py main.py
```

### exe 다시 만들기

exe는 **지금 소스를 찍어낸 사진**일 뿐이다. `z9/` 를 고친 뒤 다시 만들면 된다.

```
빌드.bat
```

PyInstaller가 없으면 알아서 설치하고, 1~2분 뒤 `dist\Z9매크로.exe` 가 갱신된다.

### 매크로는 exe 옆에 저장된다

```
dist\
  Z9매크로.exe
  data\profile.json     ← 매크로 · 시나리오 · 설정 전부
  library\              ← 보관함, 버프 아이콘
```

**exe를 옮길 때는 `data` 와 `library` 도 같이 옮길 것.** 이 두 폴더가 작업물
전부다. exe만 옮기면 빈 상태로 시작한다.

> PyInstaller로 묶으면 프로그램 파일은 실행할 때마다 임시 폴더에 풀렸다가
> 종료할 때 지워진다. 그래서 저장 위치는 그 임시 폴더가 아니라 **exe가 놓인
> 폴더**를 기준으로 삼는다 (`z9/storage.py`의 `_project_dir`).

### 반드시 관리자 권한으로 실행할 것

Z9 클라이언트(`Z9Star.exe`)는 **관리자 권한으로 실행된다.** 이 매크로가 일반
권한이면 Windows의 UIPI가 게임 창으로 가는 입력을 차단하는데, **아무 오류도 나지
않는다.** `SendInput`은 "정상적으로 보냈다"고 반환하고 입력은 조용히 버려진다.

증상은 "매크로를 켰는데 게임에서 아무 일도 안 일어남"이다. 이 도구는 시작할 때
권한을 확인해 경고하고, 권한이 부족하면 매크로 실행을 아예 거부한다. `설정` 탭의
`관리자 권한으로 다시 실행` 버튼으로 올릴 수 있다.

- 요구 사항: Windows 10/11, Python 3.11 이상 (개발·검증은 3.14.6)
- 설치할 패키지 없음

## 탭 구성

### 생활 콘텐츠
사냥 · 채광 · 벌목 · 농사 · 낚시 · 목장 프리셋을 한 번에 만든다. 콘텐츠마다
반복 구조가 다르므로 만들어지는 뼈대도 다르다.

| 콘텐츠 | 구성 | 핵심 |
|---|---|---|
| 사냥 | 순찰 경로 + 공격 연타 + 체력 조건 회복 | 셋을 따로 켜고 끔 |
| 채광 · 벌목 · 농사 · 목장 | 상호작용 키 주기 반복 + 대상 소진 감지 + 다음 지점 이동 | **주기**를 작업 시간에 맞추는 것 |
| 낚시 | 입질 픽셀 감지 → 낚아채기 | **시간이 아니라 화면 변화**로 판단 |

생성 후 각 탭에서 실제 단축키와 감지 좌표를 채워 넣어야 동작한다.

### 관찰 학습
게임 규칙을 글로 옮길 필요 없이, **평소처럼 플레이하면 도구가 지켜보고 규칙을
찾아낸다.** 손으로 좌표를 찍고 주기를 재는 작업을 대신한다.

1. `관찰 시작` → 게임 창으로 전환 → 농사(또는 목장) 동작을 평소 속도로 5~10회 반복
2. `F10`으로 중지 → `분석 실행`
3. `연타 설정으로 저장` / `감지 조건으로 저장` / `키 입력을 매크로로 저장`

관찰 중에는 사용자의 조작도 시각과 함께 남는다. 같은 동작을 다시 녹화할 필요 없이
바로 매크로로 만들어 `녹화 · 재생` 탭에서 편집할 수 있다.

동작 원리: 클라이언트 영역을 50ms마다 캡처하면서 **키 입력 시각도 같이 기록**한다.
그다음 사용자가 키를 누른 순간을 기준점으로 삼아 "그 직전에 색이 변한 픽셀"을
모든 기준점에 대해 세어 본다.

- 매번 변했다 → 신호다 (작물이 다 자람, 게이지 참, 입질 등)
- 가끔 변했다 → 캐릭터 움직임이나 이펙트 같은 잡음이다

잡음을 더 걸러내려고 **대조군**도 본다. 기준점에서 멀리 떨어진 임의 시점에서도
똑같이 변하는 픽셀은 키와 무관하므로 버린다.

```
점수 = 일관성(기준점 중 몇 %에서 변했나) × 특이성(대조군에서 안 변한 비율)
```

> 검증: 정답을 아는 합성 데이터에서 신호 위치를 정확히 찾아냈고, 무작위 깜빡임과
> 키와 무관한 주기적 변화를 모두 걸러냈다. 실제 창 규모(1366x768 → 격자 65,664점,
> 상시 움직이는 방해 영역 10곳)에서도 적중, 분석 시간 **0.33초**.

메모리를 아끼려고 원본 대신 격자로 솎아 저장한다. 격자 간격 4px 기준 1366x768
창이 프레임당 약 197KB, 초당 약 4MB다. 화면에 예상 용량이 실시간으로 표시된다.
신호가 아주 작아 놓친다면 격자 간격을 2로 줄이고 다시 관찰하면 된다.

### 녹화 · 재생
실제 조작을 그대로 기록해 재생한다.

- 기본 핫키 `F9`로 녹화 시작/정지 (설정에서 변경 가능)
- 반복 횟수(0 = 무한), 재생 속도 배율, 반복 간 대기
- 좌표는 **게임 창 클라이언트 기준 상대좌표**로 저장 → 창을 옮겨도 그대로 동작
- 창 크기가 바뀌면 좌표를 비례 보정 (옵션)

**이벤트 편집** — 녹화한 결과를 손으로 다듬을 수 있다. 매크로를 처음부터 손으로
짜는 것도 가능하다 (`+ 매크로`로 빈 매크로를 만들고 이벤트를 하나씩 추가).

이벤트 종류는 `키` · `마우스 버튼` · `커서 이동` · `휠` · **`대기`** 다.

**대기** — 아무 입력도 없이 시간만 흘려보낸다. `대기(ms)`에 값을 넣고 `＋ 대기`를
누르면 선택한 이벤트 바로 뒤에 끼워 넣는다 (종류를 `대기`로 고르고 `＋ 추가`를 해도
된다).

시각이 절대값으로 관리되므로, 대기를 **넣거나 늘리면 뒤쪽 이벤트가 그만큼 밀리고,
줄이거나 지우면 그만큼 당겨진다.** 그래야 대기 줄만 생기고 실제 길이는 그대로인
일이 없다.

```
넣기 전   0.0 A      0.5 B      1.0 C            길이 1.0초
800ms 대기를 A 뒤에
넣은 후   0.0 A   0.05 대기   1.3 B   1.8 C      길이 1.8초
```

`시각 정리 보정`은 대기 뒤의 간격을 건드리지 않는다 — 사용자가 "여기서 이만큼
쉬어라"라고 직접 넣은 것이라 보정이 덮어쓰면 넣은 의미가 없어진다.

| 기능 | 설명 |
|---|---|
| 선택에 적용 | 시각 · 종류 · 키 · 누름/뗌 · 좌표 · 휠 값을 바꿔 덮어쓴다 |
| ＋ 추가 / 복제 / 삭제 | 이벤트 단위 편집. 시각을 바꾸면 자동으로 순서가 다시 정렬된다 |
| 선택 이후 시각 이동 | 고른 이벤트부터 끝까지 통째로 ±ms 밀어 간격을 조정 |
| 키 일괄 변경 | 예: 모든 `Z`를 `X`로. 단축키를 바꿨을 때 유용 |
| 안 뗀 키 보정 | 눌린 채 끝난 키에 뗌 이벤트를 붙여 키 고착을 막는다 |
| 시작 시각 0으로 | 앞쪽 빈 시간을 잘라낸다 |
| 마우스 이동 전부 제거 | 키 위주 매크로를 가볍게 만든다 |
| 🎯 화면에서 찍기 | 좌표를 손으로 입력하는 대신 **게임 화면을 직접 클릭**해서 정한다 |

좌표 찍기는 클릭이 게임에 전달되지 않으므로 찍는 동안 캐릭터가 움직이지 않는다.
`짝 이벤트도 함께`를 켜 두면 누름/뗌 한 쌍을 같이 옮긴다 — 한쪽만 고치면 눌렀다
떼는 지점이 어긋나기 때문이다. 여러 이벤트를 골라 두고 찍으면 전부 같은 좌표가
된다.

시각은 손으로 숫자를 치지 않고 **화살표로 0.1초씩** 올리고 내린다. 스핀박스 위에서
휠을 굴려도 된다. 값이 바뀌면 선택한 이벤트에 바로 반영된다.

**휠 뭉치기** — 휠을 한 번 굴리면 이벤트가 수십 개 쏟아진다. 목록에서 읽기도 힘들고
굴림량을 바꾸려면 이벤트를 일일이 지우거나 복제해야 한다. `휠 뭉치기`를 누르면 같은
방향으로 이어진 것들을 **한 줄로 묶고 칸 수로 바꾼다**. 그다음부터는 숫자 하나만
고치면 된다.

```
휠 -120  ×6줄        →   휠   -120 × 6칸 내림
```

방향이 바뀌거나, 사이가 250ms 넘게 벌어지거나, 중간에 다른 입력이 끼면 거기서 끊는다.
`모든 휠을 [N]칸으로` 로 매크로 전체를 한 번에 맞출 수도 있다.

**자동 보정 두 가지**

| 보정 | 하는 일 | 기본 범위 |
|---|---|---|
| 누름·뗌 보정 | 키를 누르고 있는 시간을 범위 안으로 맞춘다 | 50~150ms |
| 시각 정리 보정 | 동작 사이 간격을 맞춘다 | 200~400ms |

목록에서 **`Ctrl`로 2개 이상 고르고 누르면 그 부분만** 보정한다. 이때 구간의 시작
시각은 그대로 두고, 뒤에 남은 이벤트는 줄거나 늘어난 만큼 통째로 밀어 준다 — 그래야
구간만 손봐도 전체가 깨지지 않는다. 아무것도 고르지 않으면 전체를 보정하고 시작을
0초로 당긴다. 누름·뗌 보정은 한쪽만 골라도 그 짝을 함께 처리한다.

범위는 직접 바꿀 수 있다. 누름·뗌 보정은 긴 것만 줄이는 게 아니라 **너무 짧은 것도
늘린다** — 몇 ms짜리 입력은 게임이 폴링 주기 사이에 놓쳐 아예 안 눌린 것처럼 되기
때문이다.

시각 정리 보정은 두 가지를 건드리지 않는다.

1. **누름 바로 뒤에 오는 그 키의 뗌** — 이건 '간격'이 아니라 누르고 있는 시간이다.
   여기서 벌리면 누름·뗌 보정이 무의미해진다.
2. **연속된 커서 이동** — 하나의 이어진 움직임이라 내부 리듬을 유지해야 한다.
   이걸 벌리면 20ms 간격 이동 100개가 20초짜리 매크로가 된다.

```
보정 전  간격 [0.1, 2.4, 0.1, 0.05, 0.05]   길이 2.70초
보정 후  간격 [0.1, 0.4, 0.1, 0.20, 0.05]   길이 0.85초
              ↑누름·뗌 유지  ↑0.4로 축소      ↑0.2로 확대
```

**단축키와 끌어놓기** (이벤트 목록에 포커스가 있을 때)

| 조작 | 동작 |
|---|---|
| `Del` | 선택한 이벤트 삭제 (여러 개 가능) |
| `Ctrl+C` / `Ctrl+X` | 복사 / 잘라내기 |
| `Ctrl+V` | 선택 지점 **뒤에** 붙여넣기 |
| `Ctrl+A` | 전체 선택 |
| 끌어놓기 | 순서 변경 |

붙여넣기는 뒤쪽 이벤트를 밀어서 시각이 겹치지 않게 한다. 겹친 채로 두면 같은
순간에 두 입력이 나가 게임이 하나를 흘린다.

순서 변경은 **시각 슬롯을 그대로 두고 동작만 재배치**한다. 시각이 곧 순서라
자리만 바꾸면 정렬 때 원위치로 돌아가기 때문이다. 이 방식이면 전체 리듬과 총
길이가 유지되고 "무엇을 언제 하는가"만 바뀐다.

```
변경 전   0.0 A   0.5 B   1.0 C   1.5 D   2.0 E
A를 4번째로 끌면
변경 후   0.0 B   0.5 C   1.0 D   1.5 A   2.0 E     (총 길이 2.0초 유지)
```

### 시나리오 편집기
실제로 돌리는 것은 시나리오뿐이라, **여기가 작업의 중심**이다. 매크로를 그룹으로
묶고 조건·버프·예약까지 이 화면에서 전부 설정한다.

상시 탭은 넷만 둔다 — `시나리오 편집기` · `녹화 · 재생` · `보관함` · `설정`.
연타 · 이동 경로 · 감지 조건 · 버프 · 시간 예약 · 관찰 학습 · 프리셋은 오른쪽 위
**`설정 열기`** 버튼으로 창을 띄워 쓴다. 화면은 탭에 있던 것과 같은 것을 그대로
띄우므로 기능 차이가 없다.

**단계 종류** — 그룹 안에는 네 가지를 넣을 수 있다.

| 종류 | 하는 일 |
|---|---|
| ▶ 매크로 | 녹화한 매크로 재생 |
| ⟳ 연타 | 연타를 정해진 초만큼 돌리고 다음으로 |
| ↷ 이동 경로 | 경로 실행 |
| … 대기 | 아무것도 안 하고 쉬기 |

연타는 무제한 설정이어도 시나리오 안에서는 지정한 시간(기본 10초)만 돌고 넘어간다 —
안 그러면 그 자리에서 시나리오가 멈춘다. 원본 설정은 건드리지 않는다.

`＋ 매크로 담기` 창에서 **종류를 골라** 매크로 · 연타 · 경로 중 원하는 것을 끌어다
놓을 수 있고, 단계를 선택하면 `이 항목 편집…` 으로 그 항목의 설정 창이 바로 열린다.

화면은 흐름을 그대로 보여주는 트리 하나로 되어 있다. 실행 순서가 위에서 아래로
읽히므로 시나리오가 어떻게 진행되는지 눈으로 따라갈 수 있다.

```
▼ 파밍                     3회 반복                  단계 2개
     1. 수확                뒤 300ms 대기            16개 · 1.7s
     2. 이동                뒤 1500ms 대기 (직접 지정) 4개 · 0.9s
     조건 1. HP 낮음        → 매크로 '물약' 실행       사용
     조건 2. 인벤 가득      → 시나리오 중지            사용
▼ 판매                     1회 반복                  단계 1개
     1. 상점이동            대기 없음                  8개 · 1.2s
```

**그룹** — 매크로 몇 개를 묶어 반복하는 단위. 그룹마다 반복 횟수(0 = 무한)와 단계 간
대기를 따로 준다.

**단계를 언제까지 돌릴지** — 세 가지 중에 고른다.

| 방식 | 뜻 |
|---|---|
| 항목 설정 | 매크로·경로에 저장된 반복 횟수를 따른다 (연타는 자기 시간 제한) |
| 횟수만큼 | 정한 횟수를 돌고 다음 단계로 |
| 시간 동안 | 정한 시간이 찰 때까지 되풀이하고 다음 단계로 (0.1초 단위) |

시간은 화살표로 0.1초씩 조절된다. **한 번 시작한 동작은 중간에 자르지 않는다** —
매크로를 반쯤 재생하다 끊으면 누른 키가 남거나 게임 상태가 어중간해지기 때문이다.
그래서 실제 길이는 마지막 한 바퀴만큼 더 걸릴 수 있다 (1.0초 지정 → 실측 1.01초).

항목이 무한 반복(0)으로 저장돼 있으면 `항목 설정`일 때 1회만 돈다 — 안 그러면 다음
단계로 넘어가지 못한다. 횟수나 시간을 정하면 그 값이 우선한다.

연타는 '몇 번'보다 '몇 초'가 자연스러워서 `횟수만큼`이 빠지고, 대기는 위의 쉴 시간으로
정하므로 항목 자체가 잠긴다. 어느 쪽이든 **원본 항목은 건드리지 않으므로** 같은 매크로를
자리마다 다르게 써도 서로 영향이 없다.

```
1. ▶ 수확     뒤 300ms 대기     16개 · 1.7s ×5(지정)
2. ▶ 채집     뒤 300ms 대기     8개 · 0.6s 30.0초 동안
3. ▶ 이동     뒤 300ms 대기      4개 · 0.9s
```

**단계 딜레이** — 각 단계는 기본적으로 그룹의 `단계 간 대기`를 따르지만, 단계를 골라
`이 단계 뒤 대기를 따로 지정`을 켜면 그 매크로 뒤에만 다른 값을 줄 수 있다. 대부분은
같은 간격이면 충분하고, 특정 동작 뒤에만 길게 쉬어야 하는 경우가 있어서 예외를 둘 수
있게 했다. `0`으로 지정하면 그룹값과 무관하게 쉬지 않는다.

**단계 휠 칸 수** — `휠 칸 수를 따로 지정`을 켜면 그 매크로 안의 휠 이벤트를 전부 그
칸 수로 바꿔 실행한다. 같은 스크롤 매크로를 "세 칸 내리기"와 "열 칸 내리기"로 나눠
쓰려고 복제할 필요가 없다. 원본 매크로는 건드리지 않는다.

딜레이와 휠 칸 수 모두 흐름 트리에 그대로 표시되므로 눈으로 확인할 수 있다.

**조건** — 그룹이 **한 사이클 돌고 난 뒤**에 확인한다. 조건 자체는 `조건부 실행`
탭의 감지 조건을 이름으로 가져다 쓴다. 픽셀 감지 로직을 두 벌 만들 이유가 없고,
한 곳에서 좌표를 고치면 이쪽에도 그대로 반영된다.

| 조건 동작 | 하는 일 |
|---|---|
| 매크로 실행 | 지정한 매크로를 한 번 돌리고 계속 진행 |
| 그룹으로 이동 | 지정한 그룹으로 건너뛴다 (무한 반복 그룹을 빠져나오는 방법) |
| 시나리오 중지 | 시나리오를 정상 종료 |

목록 **위에 있는 조건이 우선**이고, **먼저 걸리는 하나만** 발동한다. `사용`을 끄면
건너뛴다.

**매크로 가져오기** — `＋ 매크로 담기`를 누르면 매크로 목록 창이 뜬다. 모달이 아니라
띄워 둔 채 본 창을 조작할 수 있고, 항목을 **흐름 트리의 그룹 위로 끌어다 놓으면**
그 그룹에 들어간다. 더블클릭이나 `담기` 버튼도 된다.

| 조작 | 동작 |
|---|---|
| 끌어다 놓기 (목록 창 → 트리) | 놓은 그룹의 그 자리에 삽입 |
| 끌어놓기 (트리 안에서) | 순서 변경. 같은 종류·같은 부모끼리만 |
| `▲` `▼` | 선택 항목을 위/아래로 |
| `Del` | 선택 항목 삭제 (그룹을 지우면 안의 단계도 함께) |
| `Ctrl+C` / `Ctrl+X` / `Ctrl+V` | 단계 복사 / 잘라내기 / 붙여넣기 |

각 단계는 그 매크로의 자기 설정(반복·속도)을 그대로 쓴다. 다만 **무한 반복(0)
매크로는 시나리오 안에서 1회만** 돈다 — 안 그러면 다음 단계로 넘어가지 못한다.
원본 매크로 설정은 건드리지 않는다.

지워진 매크로를 가리키는 단계는 붉게 표시되고, 실행할 때는 건너뛰고 계속 진행한다.
한 단계가 중단되면(비상 정지, 게임 창 비활성) 시나리오 전체가 멈춘다. 조건이 서로를
가리켜 그룹 사이를 무한히 오가면 안전장치가 끊고 로그로 알린다.

옛 형식(그룹 없이 단계만 있던 시나리오)은 불러올 때 그룹 하나로 자동 변환된다.


#### 그룹 종류 — 일반 / 조건부

그룹마다 **차례대로 돌지, 조건이 걸릴 때만 끼어들지**를 정한다.

| 종류 | 언제 도나 | 끝나면 |
|---|---|---|
| **일반 그룹** | 시나리오 순서대로 | 다음 그룹으로 |
| **조건부 그룹** | 순서에서 빠진다. 조건이 걸릴 때만 | **하던 자리로 돌아온다** |

"체력이 낮으면 물약", "가방이 차면 팔러 가기"처럼 **언제 필요할지 모르는 일**을 위한
것이다. 예전에는 이런 일을 흐름 중간중간에 억지로 끼워 넣어야 했다.

조건부 그룹으로 바꾸면 세 가지를 정한다.

| 항목 | 뜻 |
|---|---|
| 발동 조건 | [조건부 실행] 탭의 감지 조건 이름. 감지 점이든 [감지 그림](#감지-그림--자리가-밀리는-것을-잡는다)이든 상관없다 |
| 확인 시점 | `사이클마다` (싸다) / `단계마다` (빠르지만 확인 비용이 든다) |
| 재발동 대기(초) | 한 번 발동한 뒤 이만큼은 다시 보지 않는다 |

**재발동 대기를 반드시 주자.** 조건이 걸린 채로 남아 있으면(가방이 아직 가득 찬 채라면)
확인할 때마다 되풀이한다. 특히 `단계마다` + 대기 0이면 단계 하나 돌 때마다 끼어들어
본작업이 사실상 멈춘다. 그래서 `단계마다`를 고르면 대기가 자동으로 10초로 채워지고,
그래도 0으로 두면 실행 시작 때 로그에 경고가 뜬다.

**끼어들기는 한 겹이다.** 끼어든 그룹 안에서 또 다른 조건부 그룹이 끼어들지 않고,
그 그룹에 달린 조건(아래 [조건])도 보지 않는다. 끼어들기는 짧고 예측 가능해야 한다 —
길게 이어지는 흐름이 필요하면 그건 일반 그룹의 일이다. 반복이 `무한(0)`이어도
끼어들 때는 1회로 끊는다. 돌아올 수 없는 끼어들기는 끼어들기가 아니다.

조건부 그룹은 흐름 목록에서 **◆** 표시가 붙고, `1회 예상 시간`에는 들어가지 않는다
(언제 몇 번 돌지 알 수 없으므로).

#### 조건 — 그룹이 한 사이클 돌고 난 뒤

그룹마다 조건을 달 수 있다. 성립하면 네 가지 중 하나를 한다.

| 동작 | 무슨 일이 |
|---|---|
| 매크로 실행 | 그 매크로를 한 번 돌린다 |
| **찾은 그림 누르기** | 감지 그림이 찾아낸 **그 자리**를 클릭한다 (자리가 정해져 있지 않은 버튼용) |
| **그룹 1회 실행 (돌아옴)** | 그 그룹을 한 번 돌고 **이 자리로 돌아온다** |
| 그룹으로 이동 (안 돌아옴) | 흐름이 그 그룹으로 옮겨 간다 |
| 시나리오 중지 | 통째로 멈춘다 |

`그룹 1회 실행`과 `그룹으로 이동`을 헷갈리지 말 것. 앞은 **끼어들기**고 뒤는 **흐름
변경**이다. 조건부 그룹을 만들어 발동 조건을 다는 쪽이 보통 더 낫지만, "이 그룹을 돌고
난 뒤에만 확인하고 싶다"면 이쪽이 맞다.

### 연타 · 홀드
키 하나를 반복한다.

- **연타**: 누름 간격 / 한 번 누름 유지 시간 / 간격 편차
- **홀드**: 정지할 때까지 계속 누르고 있기
- 토글 핫키, 자동 종료 시간
- 간격이 유지 시간보다 짧으면 자동으로 늘려 키가 겹치지 않게 한다

### 이동 경로
단계를 순서대로 실행한다. `키 누르고 있기` / `클릭` / `커서 이동` / `대기`.
좌표는 `🎯 좌표 캡처` 버튼으로 게임 화면을 클릭해서 찍는다 (클릭은 게임에
전달되지 않는다).

### 조건부 실행
화면을 감시하다 조건이 맞으면 동작을 실행한다. 보는 방법이 두 가지다.

| 무엇을 | 언제 쓰나 | 예 |
|---|---|---|
| **감지 점** — 고정 좌표의 색 | 자리가 늘 같은 것 | 체력바가 줄었나, 창이 열렸나 |
| **감지 그림** — 영역 안 어딘가의 아이콘 | **자리가 밀리는 것** | 버프 아이콘, 인벤토리 아이템 |
| **감지 숫자** — 적힌 값을 읽어 견줌 | **값 자체가 조건인 것** | 피로도 10502 / 540000 |

셋을 한 조건에 섞어 쓸 수 있고, `판정`(모두 / 하나라도)이 셋 모두에 함께 걸린다.

- 트리거: `성립할 때` / `어긋났을 때`
- 동작: 키 입력 / 녹화 매크로 실행 / 이동 경로 실행
- 확인 주기, 쿨다운, 거짓→참 전환 시에만 실행(연속 발동 방지)
- **연속 확인 횟수** — 이만큼 연달아 성립해야 진짜로 본다. 화면이 한 프레임
  깜빡이거나 다른 창이 잠깐 겹쳤을 때 헛되이 발동하는 것을 막는다
- `지금 판정 확인` 버튼으로 현재 상태와 판정 결과를 즉시 볼 수 있다

#### 감지 그림 — 자리가 밀리는 것을 잡는다

버프 아이콘은 앞엣것이 끝나면 뒤엣것이 **앞으로 당겨진다.** 어제 3번 자리였던
아이콘이 오늘은 1번 자리에 있다. 그래서 좌표+색으로는 원리적으로 잡을 수 없다.
감지 그림은 좌표를 보지 않고 **지정한 영역 안 어딘가에 그 그림이 있는지**를 본다.

여기에 한 가지가 더 겹친다 — 아이콘 위에 **남은 시간 숫자가 겹쳐 그려진다.** 그
칸은 1분마다 다른 그림이 되므로 비교에 넣으면 절대 맞지 않는다. 그래서 미리보기
위에서 **숫자 칸을 끌어 덮어 두면 그 칸은 비교에서 빠진다.**

실제로 재 본 결과다 (같은 버프, 남은 시간만 30분 → 21분 → 7분):

| | 결과 |
|---|---|
| 마스크 없이 | **3번 다 못 찾음** |
| 숫자 칸 마스크 | 3번 다 찾음 (일치도 0) |

가리지 않으면 허용 오차를 아무리 키워도 인식률은 오르지 않는다. 오탐만 는다.

**반투명 보정** — 게임 UI는 뒤 배경에 따라 통째로 밝아졌다 어두워졌다 한다.
모양은 그대로인데 값만 밀린 것이라, `반투명하게 밝기가 밀려도 같은 그림으로 보기`를
켜면 평균 차이를 먼저 빼고 비교한다. 실측으로 밝기가 40만큼 밀린 아이콘은 보정을
켰을 때만 잡혔다. (단, 48을 넘게 밀린 것은 일부러 다른 것으로 본다 — 그쯤 되면
같은 그림이라고 우길 수 없다.)

**허용 오차는 감으로 정하지 말 것** — `20회 측정` 버튼이 지금 화면의 실제 점수를
재 준다. 버프가 **걸려 있는 동안** 한 번, **끝난 뒤** 한 번 재서 두 값 사이를
고르면 된다. 예를 들어 걸렸을 때 3, 끊겼을 때 40이 나오면 허용 오차는 10~20이 안전하다.

**속도** — 순수 파이썬이라 영역이 넓을수록 느리다. 버프바 크기(360x40)에 32x32
아이콘이면 한 번에 약 50ms, 창 전체(1366x768)를 뒤지면 몇 초가 걸린다. `찾을 영역`은
**반드시** 잡아 두자. 확인 한 번이 확인 주기보다 오래 걸리면 로그에 경고가 뜬다.

**만드는 순서**

1. `＋ 그림 조건` → 이름을 붙인다
2. `화면에서 잘라내기` → 버프 아이콘의 왼쪽 위 → 오른쪽 아래를 클릭 (숫자까지 넉넉히)
3. 미리보기에서 **숫자 칸을 끌어 덮는다**
4. `영역 지정` → 버프 아이콘들이 **늘어설 수 있는 줄 전체**를 잡는다 (한 칸이 아니다)
5. `20회 측정`으로 허용 오차를 정한다
6. `성립 조건`을 `그림이 없을 때`로 두면 — 그 버프가 끊긴 순간이 조건 성립이다

그림은 보관 폴더 아래 `감지아이콘/`에 PNG로 저장된다. 마스크는 그림이 아니라 조건에
저장되므로, 같은 그림을 다른 조건에서 다르게 가려 쓸 수 있다.

#### 감지 숫자 — 값 자체가 조건일 때

피로도처럼 **숫자가 곧 조건**인 것들이 있다. `피로도: 10502 / 540000`에서 앞 값이 뒤
값에 닿으면 더 얻을 게 없으니 다른 일을 해야 한다. 색으로도 그림으로도 이건 알 수 없다.

**최대값을 적어 두지 않는다.** 뒤 값도 같이 읽어서 견주므로, 최대값이 달라지는 날에도
그대로 맞는다. 어딘가에 `540000`을 박아 두면 그 숫자가 바뀌는 날 조용히 틀린다.

**왜 일반적인 글자 인식이 필요 없나** — 게임 UI의 숫자는 사진이 아니라 비트맵 글꼴이다.
같은 숫자는 언제나 **픽셀 하나까지 똑같이** 그려진다. 그래서 모양 열 개를 한 번 익혀
두면 그 뒤로는 맞으면 완전히 맞고 아니면 확연히 다르다. 실측으로 익힌 글자의 어긋남은
**0.000**이었고, 못 익힌 자리는 `?`로 남아 조용히 틀리지 않는다.

**만드는 순서**

1. `＋ 숫자 조건` → 이름을 붙인다
2. **커서 올릴 자리** — 툴팁처럼 커서를 올려야 뜨는 것이면 그 자리를 찍는다.
   읽을 때마다 커서가 잠깐 갔다가 **원래 자리로 돌아온다**
3. **숫자 영역** — 숫자 줄만 좁게 감싼다 (`피로도 :` 같은 글자까지 넣으면 그 글자도
   익혀야 한다)
4. **숫자 모양 익히기** — `지금 화면 잘라 보기` → 잘린 글자가 확대되어 보인다 →
   보이는 대로 띄어쓰기 없이 적고 `익히기`
5. 값이 달라졌을 때 다시 눌러 **모르는 숫자를 채운다.** 0~9를 다 익히면 ✔가 뜬다
6. **언제 성립하나** 를 고른다

| 무엇을 | 뜻 |
|---|---|
| **앞 값이 뒤 값에 닿으면** | 피로도가 가득 찼을 때. 최대값이 달라져도 따라간다 |
| 비율(%) | 앞 ÷ 뒤 × 100 이 몇 % 이상/이하 |
| 앞 값 / 뒤 값 | 값 자체를 견준다 |
| 남은 양 (뒤 − 앞) | "1000 남았을 때" 처럼 |

`지금 읽어 보기`로 지금 화면에서 뭐라고 읽히는지 바로 확인할 수 있다.

**못 읽으면 성립시키지 않는다.** 툴팁이 안 떴거나 익히지 않은 숫자가 섞이면 조건은
불성립으로 두고 이유를 로그에 남긴다 — 못 읽은 것과 조건이 맞는 것은 다르다.

글꼴은 보관 폴더 아래 `숫자글꼴/<이름>/`에 숫자 하나당 PNG 하나로 저장된다. 여러
조건이 같은 글꼴을 함께 쓸 수 있다.

> **커서를 옮겨 읽는다는 뜻** — 툴팁을 띄우려면 실제로 커서를 그 자리에 올려야 한다.
> 읽고 나면 원래 자리로 돌려놓지만, 그 사이 잠깐은 커서가 움직인다. 확인 주기를
> 넉넉히(몇 초 이상) 두고, 조건부 그룹이라면 `사이클마다` 쪽이 알맞다.

### 시간 예약
`조건부 실행`이 화면을 보고 반응한다면, 여기는 **시계를 보고** 실행한다. 매시 정각처럼
정해진 시각이 오면 지정한 매크로 · 이동 경로 · 시나리오를 한 번 돌린다.

| 시각 지정 | 예 |
|---|---|
| 매시 정해진 분 | `0`분 = 매시 정각, `30`분 = 매시 30분 |
| 일정 주기마다 | `15`분마다 — 자정 기준으로 딱 떨어지는 시각에 맞춘다 |

다음 실행 시각이 화면에 실시간으로 표시된다.

**겹치지 않게 실행한다** — 이게 이 기능의 핵심이다. 돌아가는 매크로 한복판에 끼어들면
입력이 뒤섞여 게임 입장에서는 뒤죽박죽인 조작이 된다. 그래서 시각이 되어도 바로 쏘지
않고 **입력이 비는 순간**을 기다린다.

"비었다"의 기준은 두 가지다.

1. **눌려 있는 키/버튼이 하나도 없다** — 있으면 어떤 동작이 진행 중이라는 뜻이다.
2. **지정한 시간(기본 150ms)만큼 조용하다** — 이벤트와 이벤트 사이라는 뜻이다.

그 순간을 잡으면 문을 잠그고 실행한다. 다른 재생은 다음 이벤트를 보내기 직전에 멈춰
서서 기다린다 — 이미 보낸 입력은 되돌릴 수 없으니 '이벤트 사이'가 유일하게 안전한
지점이다.

제한 시간(기본 60초) 안에 그런 순간이 오지 않으면 **이번 회차는 건너뛰고** 이유를
로그에 남긴다. 억지로 끼어드는 것보다 한 번 거르는 편이 안전하다. 홀드 모드 연타처럼
키를 계속 쥐고 있는 작업이 돌고 있으면 이 경우에 해당한다.

현재 눌려 있는 입력 수가 화면에 표시되므로, 지금이 비어 있는 상태인지 눈으로 확인할
수 있다.

### 버프
지속시간이 정해진 아이템을 등록해 두면, 시나리오 그룹이 **한 사이클 돌 때마다 만료된
것만 골라 다시 쓴다.** 일해서 경험치를 얻는 동안 버프가 끊기면 그만큼 손해라, 사람이
시계를 보고 있을 필요가 없게 했다.

**남은 시간을 아는 방법 두 가지**

| 방식 | 어떻게 | 좋은 점 | 조심할 점 |
|---|---|---|---|
| **시간** | 쓴 시각 + 지속시간으로 계산 | 확실하다. 버프바가 가려져도 되고 공짜다. 앱을 껐다 켜도 타이머가 남는다 | 지속시간이 고정이어야 한다 |
| **화면** | 버프바에서 그 효과의 아이콘을 찾는다 | 다른 데서 이미 걸어 둔 버프까지 챙긴다. 지속시간이 들쭉날쭉해도 맞는다 | 버프바가 가려지면 못 본다. 확인 한 번에 0.1초쯤 |

화면 방식은 `조건부 실행`의 [감지 그림](#감지-그림--자리가-밀리는-것을-잡는다)과
같은 장치를 쓴다 — 영역 안에서 그림을 찾고, 숫자 칸은 마스크로 뺀다. 버프 아이콘은
앞엣것이 끝나면 뒤엣것이 당겨지므로 좌표로는 잡을 수 없기 때문이다.

`몇 번 연속 안 보이면 끝난 것으로 볼지`(기본 2회)를 두었다. 다른 창이 잠깐 겹쳤다고
멀쩡한 버프를 덧씌우면 아이템만 날아간다. 화면 읽기에 **실패**한 경우(창을 못 찾음
등)는 아예 손대지 않는다 — 못 본 것과 없는 것은 다르다.

| 아이템 | 지속시간 |
|---|---|
| 직업별 왕관 (농사·목장·벌목·채광·사냥·낚시별로 모양이 다름) | 15분 |
| 갈비탕 | 30분 |
| 경카 | 1시간 |
| 점검사 | 6시간 |

이름을 고르면 지속시간이 자동으로 채워진다.

**쓰는 방법 두 가지**

*퀵슬롯* — `5 6 7 8 9 0 - =` 자리에 올려 둔 아이템. 키 한 번이라 확실하다. 쓸 수
있으면 이쪽이 낫다.

*인벤토리 아이콘* — 퀵슬롯이 모자랄 때. `I`로 인벤토리를 열고, 저장해 둔 아이콘
그림을 화면에서 찾아 클릭한 뒤 다시 닫는다. 아이템 자리가 고정이 아니라 좌표로는
잡을 수 없어서 그림으로 찾는다. 실패하더라도 인벤토리는 반드시 닫는다 — 열린 채로
두면 뒤이어 돌 매크로가 전부 어긋난다.

아이콘은 **`🎯 화면에서 잘라내기`** 로 게임 화면에서 직접 뜬다 (왼쪽 위 → 오른쪽 아래
두 번 클릭). 가지고 있는 PNG를 불러올 수도 있다. 그림은 보관 폴더 아래
`버프아이콘/`에 PNG로 저장되므로 탐색기에서 확인·교체할 수 있다.

**찾는 속도** — 아이콘 탐색은 순수 파이썬이라 영역이 넓을수록 느리다. 1366x768 전체를
뒤지면 약 5초, `찾을 영역 지정`으로 인벤토리 범위만 지정하면 1초 아래로 떨어진다.
사이클마다 한 번씩만 도는 작업이라 전체 검색도 못 쓸 정도는 아니지만, 영역을 잡아
두는 편이 낫다.

일치 판정에는 허용 오차가 있다(기본 30). 게임 화면은 배경이 비치거나 살짝 어두워지는
경우가 있어 완전 일치를 요구하면 놓친다. 반대로 비슷한 아이콘이 여럿이라 잘못
잡힌다면 오차를 낮추면 된다.

**그룹에 붙이기** — 시나리오 편집기에서 그룹을 고르면 등록된 버프 목록이 나온다.
여러 개를 골라 붙일 수 있고, `만료 몇 초 전에` 값으로 미리 갱신할 여유를 준다
(기본 30초 — 정확히 만료된 순간에 쓰면 그 사이 잠깐 버프가 끊긴다).

### 업적
게임의 업적 창을 그대로 담아 두고, **일일업적을 매일 자동으로 깨는 것**이 목적이다.

목록은 [공식 가이드](https://www.z9star.co.kr/guide/info/68/)의 표를 그대로 옮긴 것이다
(2026-09-05 확인). 가이드에 없이 화면에서만 본 줄은 `※`로 표시해 둔다 — 기간 한정
이벤트일 가능성이 높아 어느 날 사라져 있어도 놀라지 않기 위해서다.

| 기간 | 개수 | 자동화 대상 | 초기화 |
|---|---|---|---|
| 일일업적 | 22 | 20 (출석하기·캐시 구매 제외) | 매일 |
| 주간업적 | 10 | 7 | 매주 월요일 |
| 월간업적 | 10 | 7 | 매월 1일 |
| 특별업적 | 3 | — (다른 업적을 하면 따라온다) | 없음 (수시로 바뀜) |

**실행은 이 탭에서 하지 않는다.** 업적마다 붙여 둔 것들로 `일일업적` 시나리오를 만들어
주고(업적 하나 = 그룹 하나), 돌리는 일은 시나리오 편집기가 맡는다. 실행 엔진을 두 벌
만들 이유가 없고, 그래야 조건·버프·자동 교정이 업적에도 그대로 걸린다.

**필요 수는 누적이다.** 농작물 수확은 1단계 35, 5단계 550인데 **550을 채우면 다섯 단계가
전부 깨진다.** 35를 채우고 다시 550을 채우는 게 아니다. 이걸 놓치면 필요한 것보다 몇 배씩
더 돌리게 된다.

```
이 단계에서 더 해야 하는 양 = 그 단계 누적값 - 앞 단계 누적값
전부 깨는 데 필요한 양      = 마지막 단계 누적값 하나
```

덕분에 **마지막 단계 값 하나만 알면 자동화가 된다.** 중간 단계를 몰라도 상관없다.

**가이드 표와 게임 화면의 숫자가 다르다.** 가이드의 '농작물 230개 수확'은 5단계에서 **더**
해야 하는 양이고, 화면의 `(0 / 550)`은 **누적**이다. 카탈로그는 가이드 값(증가분)을 받아
적고 `Spec.cumulative`가 더해서 누적을 만든다. 두 관측이 이 해석을 뒷받침한다 — 농작물
35+55+90+140+230 = 550, 동물 성장완료 12+18+30+40+50 = 150. 둘 다 화면에서 본 값과 같다.

| 업적 | 1단계 | 전부 깨려면(누적) | 전부 깨면 RP |
|---|---|---|---|
| 몬스터 사냥 | 70 | 1,090 | 100 |
| 농작물 수확 | 35 | 550 | 100 |
| 요리 생산 | 35 | 550 | 100 |
| 낚시 성공 | 30 | 400 | 100 |
| 나무 벌목 | 20 | 300 | 100 |
| 광맥 채굴 | 10 | 150 | 100 |
| 동물 성장완료 | 12 | 150 | 100 |

RP 이정표는 일일 100·150·200, 주간·월간 45·90이다. 일일업적을 전부 깨면 RP 1,085이지만
이정표는 200에서 끝나므로, **일곱 개 중 둘만 끝까지 밀면 그날 몫은 다 받는다.**

**단계 기록** — 가이드에서 다섯 단계를 다 받아 왔으므로 보통은 손댈 일이 없다. 그래도
기록 칸은 남겨 두었다. 게임은 패치로 바뀌고, 그때 붙박이 값이 조용히 틀리는 것보다
화면에서 본 값을 쓰는 편이 낫다. 값이 비어 있으면 **두 개만 쌓이면 규칙(등차/등비)을
찾아** 다음 단계를 계산하고, 규칙이 안 보이면 어림짐작 대신 모른다고 답한다. 적어 둔
값은 언제나 카탈로그보다 우선한다.

**옛 제목은 옮겨 준다.** 가이드와 표기가 달랐던 것들(`0X퀴즈`→`OX퀴즈`, 주간·월간의
`외계인 침공 방어 참가`→`외계인 침공 방어 성공`)은 프로필을 읽을 때 지금 이름으로
바꾼다. 안 옮기면 저장해 둔 설정이 카탈로그에서 짝을 못 찾아 조용히 사라진다.

**업적 하루는 새벽 4시에 넘어간다.** 화면의 '남은 시간'을 역산해 얻은 값이다 —
21:52에 6시간 8분이 남아 있었다. 자정으로 끊으면 새벽 1시에 돌린 것이 다음 날 몫으로
세어져, 정작 4시 초기화 뒤에는 아무것도 안 하게 된다. 공식 가이드는 `0시`라고 적어
두었지만 본 것을 따랐고, 가이드 표기는 `GUIDE_RESET_HOUR`로 남겨 두었다.

'했음' 표시도 기간에 맞춘다. 일일은 그날, 주간은 그 주(월요일 기준), 월간은 그 달로
센다. 주간 계획을 하루 지났다고 다시 돌리면 같은 업적을 일곱 번 돌리게 된다.

**보상 상자** — 단계를 깨도 상자를 눌러야 다음 단계로 넘어간다. 상자는 줄마다 있고
목록이 스크롤되므로 좌표를 적어 둘 수 없어서, 조건에 **`찾은 그림 누르기`** 동작을
두었다. 감지 그림이 찾아낸 바로 그 자리를 클릭한다.

### 낚시
찌를 눌러 여는 **미니게임을 대신 푼다.** 트랙에서 노란 막대와 물고기가 서로 다른
속도로 왕복하고, 겹칠 때 누르면 물고기 체력이 깎인다. 다 깎으면 클리어다.

**빗나가면 손해다** — 경험치가 줄고 물고기 체력이 회복된다. 겹칠 것 같은 자리에
미리 눌러 두는 방법은 쓸 수 없다. 반대로 **겹쳐 있는 동안에는 몇 번을 눌러도 이득이다**
— 누를수록 체력이 빨리 깎이고 판이 빨리 끝난다. 이 두 가지가 설계 전부를 결정했다.

**규칙은 하나다 — 보이면 누른다.** 이 컴퓨터에서 잰 값이다.

```
화면 한 조각 읽기      6.06ms  (판만 한 크기 616x148)
색 훑기 (620x39 띠)    0.07ms  (예전 2.8ms)
입력 내보내기          0.016ms
짧은 대기의 오차       +0.4ms
──────────────────────────────
한 장 읽는 데          6.1ms   → 초당 165장
```

**그 6ms는 우리 몫이 아니라 화면 합성 주기다.** 1000/165 = 6.06ms로 모니터 주사율과
딱 맞는다. 확인하려고 도구(DC·비트맵·버퍼)를 한 번 만들어 다시 쓰게 하고 느리다고
알려진 CAPTUREBLT 깃발도 빼 봤는데, **셋 다 초당 165장으로 똑같았다.** 캡처 경로에는
남은 여유가 없다 — 이미 화면이 그려지는 속도 그대로 읽고 있다.

크기와 무관하지는 않다. 판만 한 크기에서는 고정 비용에 묻혀 안 보이지만 1200x400은
초당 64장(17ms)으로 떨어진다. 판을 좁게 잡으라는 말은 그래서다.

**정말 중요한 것은 게임이 몇 장을 그리느냐다.** 우리가 165장을 읽어도 게임이 60장만
그리면 같은 그림을 두세 번 보는 셈이라 더 빨리 읽어 봐야 소용이 없다. [인식 검사]의
[움직임 재기]가 "찍은 장 중 새 그림이 몇 장인지"를 함께 내므로, 어느 쪽인지 눈으로
확인할 수 있다.

**읽는 속도가 곧 클릭 수다.** 겹쳐 있는 동안에만 누를 수 있고, 겹침은 몇십 ms뿐이다.
6.9ms짜리 캡처는 줄일 수 없다 — 영역을 620x155에서 620x40으로 줄여도, GDI 객체를
재사용해도 6.86~6.90ms로 똑같았다. 모니터가 새 화면을 그리는 간격(144Hz = 6.94ms)에
묶여 있다.

그래서 나머지를 줄였다. 색 훑기가 칸마다 파이썬으로 세 채널을 견주느라 620x39 띠
하나에 2.8ms, 둘이면 5.6ms를 먹고 있었다 — 캡처와 맞먹는 비용을 우리 손으로 얹고
있었던 것이다. 파이썬 반복문을 전부 C 호출로 옮겼다.

```
row[0::4]        채널 하나만 뽑아낸다 (C)
.translate(표)   허용 범위 안이면 1, 밖이면 0 (C)
정수 AND         세 채널이 모두 맞는 자리만 남긴다 (C)
.find(1)         맞은 자리로 곧장 건너뛴다 (C)
```

남는 파이썬 반복은 맞은 칸 수만큼이지 훑은 칸 수만큼이 아니다. 여기에 띠에서 여섯
줄만 뽑아 보는 것을 더해 **2.8ms → 0.07ms(40배)**, 답은 한 픽셀도 다르지 않다.
줄을 덜 보면 칸 수도 그만큼 적게 나오므로, 세어 둔 값은 띠 전체를 본 셈으로 되돌려
준다 — 안 그러면 "몇 칸 이상이면 찾은 것" 기준이 전부 뜻을 잃는다.

클릭 자체도 손봤다. 한 번 누를 때 버튼을 12ms 붙잡고 **클릭마다 커서를 다시
옮기고** 있었다. 90ms짜리 겹침에 일곱 번이 한계였던 이유다. 붙잡는 시간을 4ms로
줄이고(설정 가능), 한 구간 안에서는 자리를 옮기지 않는다.

초당 142장이면 한 번 겹쳐 있는 동안에도 열 장 넘게 본다. 그러니 어렵게 갈 이유가
없다.

```
읽는다 ─▶ 겹쳐 있으면 누른다 ─▶ 또 읽는다 ─▶ 또 누른다 ─▶ …
           가장 가까웠던 데서 4px 벌어지면 그만 누른다
```

**한동안은 이렇게 하지 않았고, 그래서 한 번도 못 눌렀다.** 앞서는 겹칠 시각을 미리
계산해 그 자리로 자러 갔다가, 깨어나서 겹쳐 있으면 눌렀다. 계산이 맞을 때는 잘 돌았다.
틀리면 도착해 보니 안 겹쳐 있고, 그러면 그대로 지나가 버렸다 — 그동안에도 겹침은 계속
일어나고 있는데 말이다. **예측을 클릭의 조건으로 둔 것이 잘못이었다.** 지금은 계산이
아무리 틀려도 겹침을 놓치지 않는다.

계산을 버리지는 않았다. 두 군데에만 쓴다.

| 어디 | 왜 |
|---|---|
| 가려서 안 보일 때 | 둘이 겹치면 하나가 다른 하나를 가려 **하필 가장 중요한 때** 못 읽는다. 그때만 직전 모델로 "지금 겹쳐 있을 것"이라 보고 누른다 |
| 게임이 늦게 처리할 때 | 지금 눈에 겹쳐 보여도 게임이 클릭을 늦게 받으면 판정할 때는 벌어져 있을 수 있다. 배운 보정(lead)만큼 앞을 내다봐 그때도 겹쳐 있을 때만 누른다 |

움직임은 등속 왕복(삼각파)으로 모델링한다. 겹칠 구간을 식으로 푸는 계산은 인식 검사
창에서 "앞으로 10초에 몇 번 겹치나"를 보여 주는 데 남아 있다. (1ms씩 굴려 보는 방식은
표본마다 2500걸음이라 2.5ms가 들었다. 식으로 풀면 0.002ms다.)

정확도를 지키는 것은 네 가지다.

| 무엇 | 왜 |
|---|---|
| 폭을 재서 튕기는 자리를 잡는다 | 물체의 **중심**은 사각형 끝까지 못 간다. 반폭만큼 안쪽에서 튕긴다 |
| 겹침 거리도 폭에서 뽑는다 | **물고기 크기가 판마다 다르다.** 고정값은 어떤 판에선 좁고 어떤 판에선 넓다 |
| 눈으로 본 겹침만 누른다 | 계산으로 "지금쯤 겹쳤겠지" 하고 누르지 않으므로, 계산이 어긋나도 헛클릭이 되지 않는다 |
| 벌어지면 즉시 멈춤 | 멀어지는 쪽이 위험하다 — 게임이 늦게 판정하면 그때는 더 벌어져 있다 |

첫 번째가 가장 컸다. 사각형 끝에서 튕긴다고 계산하면 60px짜리 물고기는 양쪽으로
30px씩 어긋난 자리를 튕김점으로 삼게 되고, 튕김을 지나는 예측이 통째로 틀린다.
게임 판정(모양이 닿으면 맞음)과 우리가 가정한 겹침을 따로 둔 시뮬레이터로 120판씩
잰 결과:

| 방식 | 클리어 | 명중률 | 헛클릭 |
|---|---|---|---|
| 예전: 사각형 끝에서 튕긴다고 봄 + 10px 고정 | 38% | 93% | 0% |
| 폭만큼 안쪽에서 튕김 + 10px 고정 | 28% | 94% | 0% |
| 겹침 거리도 폭에서 뽑음 (지금) | **100%** | 76% | 1% |

명중률이 오히려 내려간 것은 나빠진 것이 아니다. **누르는 횟수가 다르다.** 예전에는
확신이 설 때만 한 번 눌러 명중률은 높았지만 판을 못 끝냈다. 지금은 겹쳐 있는 동안
계속 누르므로 가장자리에서 몇 번은 빗나가는데, 그래도 판당 열대여섯 번이 들어가
체력이 훨씬 빨리 깎인다. **끝내는 것이 목적이지 명중률이 목적이 아니다.**

### 겹쳐 있는 내내 누른다

겹쳐 있는 동안에는 화면을 읽을 때마다 누른다 — 한 장 읽기 6.9ms + 한 번 누르기 4ms니
초당 아흔 번쯤이고, 한 번 만날 때 평균 여섯 번 들어간다.

**여기서 스스로 클릭을 깎아 먹고 있었다.** "가장 가까웠던 데서 4px이라도 벌어지면
그만 누른다"는 규칙이 있었는데, 두 물체가 같은 쪽으로 비슷한 속도로 갈 때는 겹친 채
한참 함께 간다. 가장 오래 누를 수 있는 가장 좋은 순간인데, 그동안 거리가 조금씩
출렁이므로 그 4px을 금방 넘어가 **아직 겹쳐 있는데도 멈췄다.** 멀어지는 쪽이 위험하다는
걱정은 이미 판정-시각 검사가 맡고 있으므로, 이 규칙은 손해만 남기고 걷어냈다.

### 가려진 동안에도 계속 누른다

막대가 물고기 위로 올라오면 물고기 색이 막대에 가려 **안 보인다.** 그런데 그 순간이
바로 가장 깊이 겹친 때다. 우리는 거기서 "물고기를 못 찾았다"고 보고 겹침이 끝난 줄
알아 손을 뗐다 — **가장 눌러야 할 때 멈춘 것이다.**

실제 기록이 그대로 보여 줬다. **노린 겹침 = 클릭 수**였다.

```
14.36초 · 노린 겹침 2 · 클릭 2
 7.63초 · 노린 겹침 6 · 클릭 7
```

가려졌을 때를 메우는 길이 있기는 했는데 **움직임 모델이 있어야만** 열렸다. 판이 막
시작돼 표본이 모자라면 모델이 없고, 그러면 그대로 손을 뗐다. 지금은 **닿은 것을 본
시각을 기억해** 그 뒤 0.18초까지는 안 보여도 계속 누른다 — 모델이 없어도 된다.
둘 다 다시 보이는데 갈라섰으면 그 자리에서 기억을 지운다.

| | 겹침 하나에 | 헛클릭 | 초당 |
|---|---|---|---|
| 고치기 전 | 1번 | | |
| 지금 | **28번** | 0% | 33번 |

사람은 초당 예닐곱 번쯤 누른다. 초당 33번이면 그보다 다섯 배쯤 빠르다.

### 몰아치기는 걷어냈다

겹친 것을 본 자리에서 화면을 다시 보지 않고 몇 번 더 누르는 기능을 만들어 재 봤는데
**어느 설정에서도 손해였다.** 간격을 3ms까지 좁혀도 그랬다.

```
판정이 좁은 조건 30판씩 (클리어율)
  안 함        90%
  2번 · 3ms    17%
  2번 · 10ms   40%
  5번 · 10ms    7%
```

까닭은 뚜렷하다. 화면 한 장 읽는 데 6ms, 한 번 누르는 데 4ms라 **이미 11ms마다 누르고
있다.** 30ms 간격 몰아치기는 그보다 느리다. 아낄 것이 없는데 눈만 감는 셈이라, 그 사이
물체가 창을 벗어나면 뒤쪽 클릭이 죄다 빗나가 체력을 도로 채운다.

가려진 동안을 가장자리 기억으로 메우게 되면서 한 겹침에 스물여덟 번씩 누르게 됐으니,
몰아치기가 채우려던 자리도 없어졌다.

### 기록 — 무엇이 낚음 주기를 줄이는가

돌아가는 동안 있었던 일을 `data/fishlog/` 에 JSON Lines로 남긴다. 한 줄에 한 가지 일,
세션마다 파일 하나다. 가장 중요한 값은 **낚음 주기** — 한 마리 낚고 다음 마리 낚기까지
걸린 시간이고, 이것이 짧아지는 쪽이 곧 좋아진 것이다. 클리어율도 명중률도 결국 여기로
모인다.

```
start   그때의 설정 전부 + 배워 둔 lead·배수
cast    던짐          nudge  두드리다 지쳐 다시 던짐
round   판 결과 (걸린 시간·클릭·명중·쓴 창 너비·배수)
caught  낚음 + 직전 낚음과의 간격  ← 이것이 주기
dig     땅 파기 (얼음낚시)         end  세션 합계
```

[기록 보기]를 누르면 세션들을 한 표로 견주고 주기가 가장 짧았던 설정을 짚어 준다.
**기록이 낚시를 방해하면 안 되므로** 쓰기는 전부 감싸 두었고, 한 번 실패하면 조용히
그만둔다.

### 겹쳤다고 볼 거리를 스스로 좁힌다

잰 그림 폭에서 뽑은 거리는 "두 그림의 가장자리가 닿는 순간"이다. 그런데 **게임이
맞았다고 치는 자리는 그보다 훨씬 좁을 수 있다.** 물고기 그림이 90px이라고 게임이
90px 내내 맞다고 해 주지는 않는다 — 그림에는 지느러미며 여백이 있다.

실제로 이것 때문에 크게 틀렸다. 잰 폭으로 창을 잡고 그 안에서 쉬지 않고 눌렀더니,
누른 것의 대부분이 빗나가 **도로 체력을 채워 줬다.** 빗나감은 헛일이 아니라 깎아 둔
것을 되돌리는 손해다(시늉에서 맞힘 7.1, 빗나감 +9).

얼마나 좁혀야 하는지는 물고기마다 판마다 다르고 사람이 알 길이 없다. 다행히 **정답은
화면에 있다** — 누르고 체력이 줄면 맞은 것이다. 그래서 lead와 같은 방식으로 배수
후보를 돌려 가며 써 본다.

**명중률로 고르면 안 된다. 여기서 한 번 크게 틀렸다.** 처음에 lead와 똑같이 명중률로
골랐더니 배수가 0.2까지 쪼그라들었다. 아주 좁게 잡으면 누르는 족족 맞으니 명중률은
100%가 되는데, **판당 클릭이 15번에서 8번으로 줄어 물고기가 안 죽는다.** 클리어율이
100%에서 28%로 무너졌다. 맞히는 것이 목적이 아니라 판을 끝내는 것이 목적이다.

지금은 **초당 깎은 체력**으로 고른다. 빗나가면 체력이 도로 차오르므로 그 손해까지
저절로 셈에 들어간다. 시간은 그 배수를 쓰기로 한 순간부터 재므로, 좁게 잡아 겹침을
통째로 놓친 시간도 그 배수의 잘못으로 셈해진다.

게임의 진짜 판정 폭을 바꿔 가며 잰 값 (우리가 잡는 창은 40px, 40판씩):

| 게임의 진짜 판정 | 예전 (1.0 고정) | 스스로 배움 | 배운 배수 |
|---|---|---|---|
| 40px | 100% | 95% | 1.0 |
| 24px | 100% | 95% | 1.0 |
| **16px** | **35%** | **95%** | **0.5** |
| 10px | 10% | 10% | — |

16px 줄이 신고된 상황이다 — 창의 절반 넘게가 헛클릭이던 경우로, 클리어율이 35%에서
95%로 올랐고 판당 클릭은 147번에서 25번으로 줄었다. 성적표를 보면 40px × 0.4 = 16px로
**진짜 판정 폭을 그대로 찾아냈다.**

이미 잘 되던 자리(40·24px)에서는 후보를 둘러보는 값만큼만(100% → 95%) 치른다.
**10px 줄은 솔직히 적어 둔다** — 게임의 판정이 그림보다 네 배 넘게 좁으면 어느 쪽으로도
안 된다. 배우는 쪽이 손해를 키우지도 않지만 구해 주지도 못한다.

**겹침 비율(수동 설정)은 1.0이다** — 닿기만 하면 겹친 것으로 본다. 여기에 위의 배운
배수가 곱해진다.
처음에는 0.8로 안전 여유를 뒀는데, 겹쳐 있는 시간이 짧아지는데 그중 20%를 스스로
버리는 셈이라 물체가 빠를 때 손해였다.

| 속도 | 비율 0.8 | 비율 1.0 |
|---|---|---|
| 기본 | 100% (헛클릭 0%) | 100% (1%) |
| 2배 | 100% (0%) | 100% (1%) |
| 3배 | 98% (0%) | **100%** (2%) |
| 4배 | 95% (0%) | **100%** (2%) |

**보이면 누르기로 바꾼 뒤 이 차이가 많이 줄었다.** 예전에는 4배 속도에서 29% 대
81%로 갈렸다 — 기회를 하나 놓치면 다음 겹침까지 통째로 기다려야 했기 때문이다.
지금은 한 겹침에 열 번 넘게 누르므로 좁게 잡아도 어지간히 메워진다. 그래도 1.0이
낫고, 대신 헛클릭 1~2%를 치른다. 1.1로 넘기면 그때부터 헛클릭이 는다.

모델만 믿고 덤으로 몇 번 더 누르는 것도 재 봤는데 손해였다(클리어 100% → 8~90%로
들쭉날쭉). 판정선에 바짝 붙여 두었으므로 모델이 몇 px만 어긋나도 그 덤 클릭이 그대로
빗나감이 되고, 빗나감은 체력을 되돌려 눌러서 깎은 것을 도로 물어 준다.

조건을 흔들어도 마찬가지다. 판 120회씩:

| 조건 | 클리어 | 헛클릭 | 판당 클릭 |
|---|---|---|---|
| 기본 | 100% | 1% | 15 |
| 물체 2~4배 속도 | 100% | 1~2% | 15~16 |
| 물고기 반폭 12px / 55px | 100% | 1% | 15 |
| 게임이 30ms 늦게 처리 | 100% | 6% | 19 |
| 느린 PC (캡처 12ms) | 100% | 1% | 15 |
| 겹치면 ±25/±35px 안 보임 | 100% | 1% | 15 |
| 화면 50% 드롭 | 100% | 1% | 15 |

게임 지연 30ms에서만 헛클릭이 6%로 오른다. 눈에 겹쳐 보이는 것과 게임이 판정하는
순간 사이가 그만큼 벌어지기 때문인데, 그래도 판당 클릭이 19번으로 늘어 클리어는
지킨다.

겹침을 골라 노리는 일도 그만뒀다. 예전에는 "모델이 최근 표본과 잘 맞고, 겹치는 시간이
우리 오차보다 넓고, 너무 먼 미래가 아닐 때만" 눌렀다. 조건 하나가 어긋날 때마다 기회가
통째로 날아갔고, 시간이 빠듯해지면 기준을 낮추는 예외까지 달아야 했다. 보이는 겹침을
전부 누르는 지금은 그런 조건이 하나도 없다 — 판당 클릭이 열대여섯 번으로 늘었고,
그러면서 헛클릭은 1%다.

**화면에서 읽는 것은 네 가지다** — 막대 x, 물고기 x, 체력 비율, 남은 시간(보이는지).
전부 **한 줄이 아니라 띠(band)로** 훑는다. 처음에는 y 한 줄만 봤는데 실제로 써 보니
그대로 망가졌다. 사람이 그 한 줄을 정확히 짚어야 하고, 물고기처럼 속이 빈 그림은
하필 그 줄에 아무것도 안 걸린다. 열 줄을 더 봐도 1ms가 안 든다(캡처 6ms에 비하면
없는 셈이다).

체력은 길이가 아니라 **비율**이다. 게이지에 눈금이 그어져 있어서 칸을 세면 눈금만큼
모자라게 나오므로, 남은 색이 닿은 **가장 오른쪽까지의 길이 ÷ 전체 길이**로 잰다.
전체 길이는 깎이기 전 길이라 색만 찍어서는 알 수 없고, 사람이 끌어서 잡아 줘야 한다.

### 소리로 낚음을 가린다

**스피커로 나가는 소리를 되받아 듣는다**(WASAPI 루프백). 마이크가 아니므로 볼륨을
줄여 두어도, 이어폰을 꽂아도 들린다. 외부 라이브러리를 안 쓰기로 한 프로젝트라
COM vtable을 ctypes로 직접 두드린다.

```
MMDeviceEnumerator ─▶ 기본 재생 장치
                      └─▶ IAudioClient (LOOPBACK 켜고 Initialize)
                            └─▶ IAudioCaptureClient ─▶ 소리 조각들
```

여기서 하루를 날릴 뻔한 함정이 하나 있었다. **`WAVEFORMATEX`에 `_pack_ = 1`이
없으면 안 된다.** 필드를 더하면 18바이트인데 그 안에 4바이트짜리가 있다는 이유로
ctypes가 20바이트로 부풀린다. 윈도우는 18바이트로 주므로 뒤따라오는 `SubFormat`이
통째로 밀려서, **32비트 실수 소리를 정수로 잘못 읽는다.** 소리는 잡음이 되는데
아무 오류도 안 난다. 형식이 "32비트 정수"로 나오는 것을 보고서야 알았다 — 공유
모드 믹스 형식은 거의 언제나 실수다.

**소리 크기가 아니라 결로 가린다.** 크기만 보면 배경 음악에 그대로 속는다. 어느
높이가 얼마나 섞였는지를 열두 대역으로 재서 배워 둔 것과 견준다.

```
소리 조각(0.04초) ─▶ 4분의 1로 솎기 ─▶ 열두 높이의 세기 ─▶ 길이 1로 맞추기
                                                              │
                                          배워 둔 결과 견주기 ◀┘
```

높이별 세기는 **괴르첼**로 낸다. 푸리에 변환을 통째로 하면 안 쓸 수천 개 높이까지
다 나오는데 우리는 열두 개뿐이다. 그래도 파이썬 반복문이라, 먼저 4분의 1로 솎아
(44.1kHz → 11kHz) 셈을 네 배 줄인다. 효과음의 결은 5.5kHz 아래에 다 있다. 한
조각에 0.4ms다.

**창함수(해닝)를 안 씌우면 없던 높이가 새어 나온다.** 880Hz를 넣었더니 740Hz도
1040Hz도 아닌 520Hz가 가장 세게 나온 적이 있는데, 조각이 뚝 끊긴 자리 때문이었다.
앞뒤를 부드럽게 깎으니 제자리를 찾았고, 서로 다른 소리의 닮은 정도가 0.0035에서
**0.0000**으로 떨어졌다.

세기를 길이 1로 맞추므로 **볼륨을 바꿔도 그대로 알아본다** — 45배 차이를 두고 재도
닮은 정도가 0.9999 위다.

진짜 스피커로 소리를 내어 재 본 값:

| 무엇 | 닮은 정도 |
|---|---|
| 배운 그 소리 | 0.95 ~ 0.99 |
| 딴 효과음 | 0.40 ~ 0.66 |
| 고요 | 0.00 |

**"이보다 작은 소리는 무시" 문턱이 생각보다 중요하다.** 그걸 0.004로 두고 재 봤더니
아무 소리도 안 나는데 닮은 정도가 0.795까지 올라왔다 — 고요의 결이란 곧 잡음의
결이고, 잡음은 아무 모양이나 될 수 있기 때문이다. 기본값 0.03이면 0으로 떨어진다.

소리를 듣는 일은 **따로 도는 실**이 맡는다. 화면은 언제 찍어도 그때 것이 나오지만
소리는 그때 안 받아 두면 사라진다. 미니게임을 푸느라 몇 초씩 딴짓하는 동안에도
놓치지 않으려면 받아 둘 사람이 따로 있어야 한다.

**루프백은 컴퓨터에서 나는 소리 전부를 듣는다.** 게임 것만 골라 들을 수는 없으므로,
하필 결이 닮은 소리가 다른 데서 나면 속을 수 있다. 그때는 문턱을 올린다.

### 시간을 낭비하지 않는다

낚음을 알아보는 세 근거가 **모두** 어긋나면 이미 낚아 놓고도 계속 머리 위만 두드리게
된다. 그 상태는 아무 일도 안 일어나므로 스스로 빠져나올 길이 없고, 예전에는 입질
대기(기본 40초)가 다 지나야 풀렸다. 그 40초가 고스란히 낭비였다.

**두드리기만 이어진 시간**을 따로 재서 끊는다. 기본 5초, 0.1초 단위로 정한다.
미니게임을 푸는 동안은 이 시간을 세지 않는다 — 30초짜리 판을 풀고 나왔다고 해서
"두드리기만 30초 했다"가 되면 안 된다.

### 버프

낚시에 걸어 두는 버프가 둘이고 유지 시간이 다르다. 낚시를 시작하는 그 순간에 걸고,
시간이 다 되면 다시 건다.

```
처음      [1] → [7] →(1초)→ [8] → [0]×23 → [6]
다시 걸 때 [1] → [만료된 버프키] → [0]×N → [6] → [ctrl]

          [7]  3분 유지 · 걸고 나서 [0] 4번
          [8] 10분 유지 · 걸고 나서 [0] 19번
```

처음에 [0]을 23번 누르는 것은 두 몫을 한 번에 하기 때문이다(4 + 19 = 23).

**만료되자마자 걸지 않는다.** 낚시 도중에 키를 누르면 그 판이 통째로 날아가므로,
다음에 한 마리 낚을 때까지 기다렸다가 그 틈에 건다 — 낚음 뒤에는 어차피 다시 던져야
하니 공짜다. 둘 다 만료됐으면 이어서 걸고, 낚싯대는 마지막에 한 번만 든다.

### 얼음낚시

낚시터가 두 군데다. **일반 낚시터는 아무것도 더 할 것이 없다.** 얼음낚시터는 땅이
다시 얼어붙어서, 얼면 낚시가 안 되므로 때맞춰 다시 파야 한다. 파는 동안은 낚시가
끊기므로 파고 나서 다시 던져야 한다.

```
5분마다 ─▶ [5] ─▶ [ctrl] ─▶ [6] ─▶ [ctrl] ─▶ 낚시로 돌아감
```

키 차례는 글로 적어 두고 그대로 누른다(기본 `5, ctrl, 6, ctrl`). 주기는 1초 단위다.
마지막 [ctrl]이 낚시를 다시 시작하는 몫이라, 판 뒤에는 던진 것으로 치고 시계들을
다시 맞춘다.

**미니게임을 푸는 도중에는 절대 안 판다.** 그때 키를 누르면 그 판을 통째로 날린다.
판이 떠 있으면 판부터 풀고 끝난 뒤에 판다 — 시험에 그대로 박아 두었다.

시작할 때 한 번 먼저 판다. 이미 파 둔 땅이면 헛일이지만, 언 땅에서 시작하면 첫 주기가
다 지나도록 아무것도 못 낚는다.

### 실제 기록이 잡아낸 것

기록을 붙이자마자 실제 2분치에서 두 가지가 나왔다.

```
판 46 · 그중 41판이 0.1~0.3초에 클릭 0번으로 끝남 (aborted)
그 41판의 잰 폭 = 막대 0px · 물고기 2px
진짜 판 5개의 잰 폭 = 막대 20px · 물고기 499px   ← 트랙이 518px인데!
```

**41판이 미니게임이 아니었다.** 물고기 색이 세로로 길쭉하게 조금 걸린 것만으로 판이라
보고 들어가, 아무것도 못 하고 나왔다. 한 판마다 창이 닫히기를 기다리고 쉬는 시간까지
보내니 **머리 위를 두드릴 틈이 사라졌다** — "연타가 안 된다"는 신고의 정체였다. 지금은
근거가 **둘 이상**이어야 들어간다(시간표시는 미니게임에만 있으므로 그것 하나면 충분).

**물고기 폭 499px은 배경이 그 색에 걸린 것이다.** 그 폭에서 뽑은 겹침 거리는 207px,
트랙의 40%다. 사실상 늘 겹쳤다고 보고 누르고 있었다.

여기서 **고치다가 더 크게 망가뜨렸다.** "트랙 절반을 넘으면 물고기가 아니다"라고
통째로 물리쳤더니, 그 설정에서는 물고기 자리가 아예 없어져 **미니게임에서 클릭이 한
번도 안 나갔다.** 폭이 오염됐다고 자리까지 틀린 것은 아니다 — 가운데는 맞은 칸들의
평균이라 가장자리 잡티 몇 개에 거의 안 흔들리고, 실제로 그 설정에서도 겹침 정확도는
높았다. 지금은 **폭만 버리고 자리는 살린다.** 폭을 못 재면 사람이 정해 둔 값으로 물러선다.

### 낚았는지 어떻게 아는가

미니게임을 깬 뒤가 오히려 자주 막혔다. 판이 사라지면 [ctrl]을 눌러 낚시중으로
되돌려야 하는데, 예전에는 **빨간 글씨를 본 뒤에야** 던졌다. 그 글씨를 한 번 놓치면
이미 낚아 놓고도 머리 위만 하염없이 두드렸다 — 낚시가 거기서 통째로 멈춘 것이다.

**다시 던지는 일과 낚은 수를 세는 일을 갈라 놓았다.** 판이 사라졌다는 것은 낚았거나
실패했거나 둘 중 하나이고, 어느 쪽이든 지금 낚시중이 아니라는 뜻이다. 그러니 근거를
못 봐도 던진다. 세는 쪽은 틀려도 손해가 작지만, 던지는 쪽이 막히면 낚시 자체가 멈춘다.

```
판이 사라짐
  ├─ 낚음 근거를 봤다  ─▶ [낚음] 한 마리 세고 다시 던짐
  └─ 못 봤다           ─▶ [다시 던짐] 세지는 않고 던지기만
```

근거는 셋이고 **하나만 서도 낚은 것으로 본다.** 셋은 서로 다른 이유로 놓친다.

| 근거 | 무엇 | 언제 놓치나 |
|---|---|---|
| ⓪ 성공 효과음 | 성공할 때 울리는 소리 | 하필 닮은 소리가 딴 데서 날 때 |
| ① 성공 알림 | 왼쪽 위 빨간 글씨 「○○ 떡밥 1개가 차감됐어요」 | 다른 것에 가리거나 뜨는 자리가 밀릴 때 |
| ② 낚싯대 흔들림 | 낚싯대 끝에 매달린 물고기가 대롱대롱 | 물고기가 하필 멈춘 순간 |

**⓪이 가장 든든하다.** 나머지 둘은 결국 화면을 보는 것이라 창이 가리거나 자리가
밀리거나 움직임이 미세하면 그대로 못 본다. ①은 실제로 자주 놓쳤고, ②는 흔들림이
너무 미세해 문턱을 잡기 어려웠다. 소리는 그런 것에 안 걸린다.

②가 새로 들어온 것이다. **색으로 자세를 가리려던 것은 실패했다** — 낚시중 자세와
낚은 자세는 색이 거의 같다. 하지만 낚았을 때는 물고기가 매달려 쉬지 않고 까딱거리므로,
색이 아니라 **바뀌는 것**을 보면 갈린다. 물고기 종류가 여러 가지라 색도 모양도 매번
다른데 흔들림은 종류를 안 가리니, 오히려 빨간 글씨보다 든든하다.

바뀐 칸을 세는 것도 파이썬 반복문 없이 한다 — 색 훑기와 같은 수법이다.

```
buf[off::4]      채널 하나만 뽑는다 (C)
.translate(표)   허용차 안쪽 차이를 뭉갠다 (C)
정수 XOR         달라진 자리만 남는다 (C)
.count(0)        그대로인 칸을 센다 (C)
```

60×60 자리 한 번에 0.028ms다. 다만 **눈금 표를 한 장만 쓰면 경계에서 헛걸린다** —
허용차 16에 10과 18은 8밖에 안 다른데 10//16=0, 18//16=1이라 "바뀌었다"가 된다.
흔들림이 미세한 만큼 이런 헛걸림이 그대로 오탐이 된다. 그래서 눈금을 반 칸 엇갈린
표를 하나 더 두고 **두 장 모두에서 달라진 칸만** 센다.

**절대 문턱을 사람이 맞히게 했더니 못 맞혔다.** "한 장에 몇 칸 넘게 바뀌면 움직임"을
재서 넣게 했는데, 자리마다 물고기마다 배경마다 값이 딴판이라 한 번 잘 맞춘 값도 다음
판에는 안 맞았다. 그러면 아무리 흔들려도 그냥 못 알아본다 — 실제로 그렇게 못 썼다.

지금은 **바탕을 스스로 잰다.** 그 자리를 늘 보고 있으므로 조용할 때가 어느 만큼인지는
저절로 쌓인다.

```
바탕    45초 동안 본 것 중 아래쪽 10분의 1 (조용할 때가 이만큼)
문턱    바탕 × 3배 — 자리를 옮겨도 물고기가 달라져도 저절로 따라간다
되풀이  1.2초 안에 문턱을 넘은 장이 4개는 나와야 한다
```

마지막 겹이 핵심이다. **대롱대롱은 한 번이 아니라 되풀이다.** 창이 하나 뜨거나 다른
캐릭터가 지나가는 것은 한 번 튀고 마는데, 매달린 물고기는 보는 내내 까딱거린다.

**바탕을 짧게 보면 제 꼬리를 문다.** 처음에 최근 12초치의 아래쪽 5분의 1로 잡았더니,
물고기가 쉬지 않고 까딱거릴 때 그 12초가 통째로 "움직이는 중"이라 바탕까지 60칸으로
올라갔다. 문턱은 그 세 배인 180칸이 되고, 그러면 **아무리 흔들려도 못 알아본다.**
시험이 이걸 잡아냈다. 지금은 45초를 본다 — 낚시는 기다리는 시간이 길고 낚은 순간은
짧으므로, 45초 안에는 반드시 조용하던 때가 들어 있다. 같은 까닭으로 **자세가 바뀌어도
바탕은 안 버린다.**

한때 느린 흔들림을 놓칠까 봐 **가장 오래된 장과도 견주어** 큰 쪽을 썼다. 그랬더니
한 번뿐인 변화가 오래된 장이 밀려날 때까지 몇 장 내리 "많이 바뀜"으로 나와 흔들림처럼
보였다. 지금은 바로 앞 장하고만 견주고, 느린 흔들림은 **찍는 간격**(기본 0.1초)으로
맞춘다.

빨간 글씨를 살피는 간격도 손봤다. 두드리는 동안 상태 기계는 초당 백 번 도는데 그때마다
찍으면 캡처 하나에 6.9ms라 코어를 통째로 태운다. 0.05초에 한 번으로 줄이되, **판이
끝난 직후와 다시 던진 직후에는 곧바로** 살핀다 — 그때가 가장 중요한 때다.

**설정 화면이 첫 판에서 그대로 실패했다.** "누르면 색, 끌면 범위"로 만들었더니
사용자가 막대 위에서 끌어 트랙 범위가 `389~409`(막대 폭)이 됐고, 저 멀리 있는 물고기는
영원히 못 찾았다. 물고기 색도 막대에서 찍혀 있었다. 그래서 두 가지를 바꿨다 —
**지금 무엇을 하는 중인지 화면에 적고**(`→ 그림에서 물고기의 색을 찍으세요`),
**색을 찍으면 범위를 대신 잡아 준다.** 좌우로 움직이는 것(막대·물고기)은 x를 판
전체로 열고, 제자리에 있는 것(체력·시간)은 찾은 자리로 좁힌다.

그 자동 범위 잡기에서 두 번째 결함이 나왔다. **색을 찍을 때마다 범위를 다시 계산해
기존 것과 합쳤더니**, 물고기의 희끄무레한 색이 물방울과 판 테두리에도 묻어 있어서 띠가
`y 0~142`(판 전체)로 부풀었다 — 애써 끌어 둔 트랙 영역이 통째로 망가진 것이다. 합치기는
되돌릴 수도 없었다(넓어지기만 하고 좁아지지 않으니까). 규칙을 단순하게 바꿨다:
**색 찍기는 색만 바꾸고, 범위는 아직 없을 때만 대신 잡는다.**

처음 잡을 때도 "판에서 가장 진한 곳"을 찾으면 안 된다. 판 테두리는 한 줄이 판 폭만큼이라
늘 그쪽이 이긴다. **찍은 자리에서 위아래로 번져 나가며 색이 끊기는 데서 멈춘다** — 찍은
것과 이어져 있지 않은 것은 아무리 진해도 안 딸려 온다.

막대와 물고기 색이 서로 구별이 안 되면(실제로 `#E7EFF7`과 `#CEDEEF`이 찍혀 있었다) 둘 다
엉뚱한 것을 잡으므로, 그런 색을 찍으면 경고한다.

세 번째 결함은 더 근본적이었다. **막대와 물고기가 범위 하나를 함께 쓰고 있어서**, 물고기
영역을 끄는 순간 막대 영역이 사라졌다. 사용자가 알려 준 것은 화면 설계가 게임과 어긋나
있다는 것이었다 — 사각형은 물체가 **있는 자리**가 아니라 **왔다 갔다 하는 범위**다. 그래서
셋으로 나눴다.

| 항목 | 무엇을 정하나 |
|---|---|
| 움직이는 범위 | 막대와 물고기가 오가는 사각형. **가로를 둘이 함께 쓴다** |
| 트랙 막대 | 색 + **세로만** |
| 물고기 | 색 + **세로만** |

가로를 물체가 지금 서 있는 자리로 좁히면 반대편으로 간 순간 놓치므로, 움직이는 것의 가로는
언제나 [움직이는 범위]에서 빌려 온다. 세로를 나눠 두면 막대(트랙 높이를 꽉 채움)와
물고기(가운데만 차지)가 서로에게 덜 속는다.

**돌리기 전에 [인식 검사]로 확인한다.** 설정이 조금 어긋나면 낚시를 시작해도 아무 일도
안 일어나고 왜 그런지 알 길이 없다. 그래서 화면을 계속 읽어 보여 주기만 하는 창을
따로 뒀다 — 막대·물고기 숫자가 오가는지, 체력이 %로 나오는지, 찌와 낚는 모션이 뜰 때
반응하는지. 여기서는 아무것도 누르지 않는다.

**클릭 범위는 사각형으로 받아 그 안에서 무작위로 고른다.** 늘 같은 한 점을 누르면
사람이 아닌 티가 나고, 하필 그 자리에 다른 UI가 겹치면 통째로 망가진다. 겨누는 일은 판이
열릴 때 한 번만 하고, 겹친 동안 누르면서는 커서를 다시 옮기지 않는다.

**지연 보정은 스스로 배운다.** 겹치기 몇 ms 전에 눌러야 맞는지는 컴퓨터와 게임 사정에
따라 다르다. 처음에는 "빗나가면 한 방향으로 밀고 세 번 이어 빗나가면 뒤집는다"로
만들었는데 **제자리를 맴돌기만 했다** — 빗나감 한 번은 이르게 눌렀는지 늦게 눌렀는지
알려주지 않기 때문이다. 그래서 후보 값(-60ms ~ +60ms)을 돌려 가며 써 보고 성적을 적어
둔 뒤 가장 좋은 값을 쓰는 방식으로 바꿨다. 배운 표는 프로필에 남아 판을 넘겨 이어진다.

**겹치는 순간에는 화면을 못 읽는다.** 하나가 다른 하나를 가리기 때문인데, 하필 가장
중요한 순간이다. 처음에는 한 장만 못 읽어도 표본을 통째로 지우고 모델을 다시 세웠다.
그러면 다시 열두 장을 모을 때까지 가려진 동안을 메울 길이 없고 그 사이에 기회가
지나간다. 지금은 **직전 모델로 메운다** — 왕복 운동은 화면을 못 읽는 동안에도 그대로
이어지므로 몇 장 놓쳤다고 계산이 틀려지지 않는다. 다만 직전 0.12초 안에 실제로 붙어
오는 것을 본 경우로 한정한다. 멀리 있다가 갑자기 안 보이는 것은 겹침이 아니라 그냥
놓친 것이다. 시간이 빠듯한 조건(14번 맞혀야 클리어, 제한 9초)에서
잰 차이:

| 조건 | 끊기면 버림 | 모델 유지 |
|---|---|---|
| 가림 없음 | 26% | 26% |
| 겹치면 ±25px 안 보임 | 15% | 23% |
| 겹치면 ±45px 안 보임 | **5%** | **19%** |
| 50% 드롭 | 19% | 27% |
| 80% 드롭 | **0%** | **22%** |

표본 창도 12개(70ms)에서 48개(0.3초)로 늘렸고, 위상을 마지막 표본에 걸지 않는다.
마지막 한 장이 1px만 흔들려도 모델 전체가 밀리고 그 밀림이 1초 뒤 예측에서는 몇십
px이 된다. 대신 모델을 시간축으로 조금씩 밀어 보며 최근 표본 전체와 가장 잘 맞는
자리를 고른다.

인식 검사 창에서도 하나 나왔다. `_tick`이 다음 차례를 예약하면서 **이미 잡아 둔
예약을 취소하지 않아서**, 밖에서 한 번 더 부를 때마다 타이머 사슬이 하나씩 늘어났다.
늘어난 사슬은 어디서도 못 멈춘다 — 검사에서 초당 다섯 번이어야 할 읽기가 545번
돌았다.

명중 판정에도 함정이 있었다. 클릭 후 **정해진 시각에 한 번 보고** 판정하면, 게임이
클릭을 늦게 처리할 때 그 시각에는 아직 아무 일도 안 일어나 있다. 맞은 것을 빗나갔다고
세고 그 성적으로 보정을 배우니, 지연 60ms에서 명중률이 0%가 됐다. 지금은 **줄어드는
것을 보면 맞음, 기한(0.25초)까지 안 줄면 빗나감**으로 센다.

가상 시계 시뮬레이터로 조건마다 120판씩 잰 결과(14번 맞혀야 클리어, 빗나가면 9 회복,
제한 20초):

| 조건 | 클리어 | 명중률 | 보고 누르기 |
|---|---|---|---|
| 기본 ±10px | 98% | 91% | 100% |
| 빡빡함 ±5px | 98% | 90% | 100% |
| 아주 빡빡 ±3px | 98% | 89% | 100% |
| 게임 지연 30ms | 98% | 91% | **28%** |
| 느린 PC (캡처 12ms) | 98% | 91% | — |

지연이 없으면 보고 눌러도 된다. 차이는 **지연이 생길 때** 난다. 배우는 lead도 지연을
따라간다 — 0/15/30/45/60ms에서 +0/+10/+40/+40/+50ms를 골랐다. 90ms를 넘으면 후보 범위
밖이라 못 맞춘다.

**찌를 알아보려 하지 않는다.** 처음에는 색으로, 그 다음에는 그림 맞추기로 찌를
찾았는데 둘 다 놓치기 일쑤였다 — 작고 잠깐 뜬다. 지금은 **찌가 보이든 안 보이든
그 자리를 0.1~0.3초마다 계속 두드린다.** 헛클릭은 아무 해가 없고, 미니게임 인식은
잘 되므로 뜨는 순간 두드리기를 멈추고 겹침 예측 클릭으로 넘어가면 된다. 알아보기
어려운 것을 알아보려 애쓰는 대신, 알아보기 쉬운 것(미니게임)을 관문으로 삼았다.

**성공 판정도 자세가 아니라 알림 글씨로 한다.** 낚는 자세와 낚시중 자세는 색이
거의 같아 견주기가 까다로웠다. 대신 성공하면 창 왼쪽 위에 뜨는
「○○ 떡밥 1개가 차감됐어요」 **빨간 글씨**를 본다. 떡밥 종류가 많아 글자는 매번
다르지만 색은 늘 같으므로, 글자를 읽지 않고 그 색이 몇 칸 보이는지만 세면 된다.
글자를 읽으려 들면 떡밥 이름을 전부 가르쳐야 하고, 하나라도 빠지면 그때부터 못 센다.

글씨는 몇 초 떠 있으므로 **없다가 생긴 순간**만 센다. 떠 있는 내내 세면 한 마리를
여러 번 센 것이 되고, 그때마다 다시 던져 낚싯대를 거둬 버린다.

그래서 흐름은 이렇다.

```
낚시중 ─ 머리 위를 0.1~0.3초마다 두드린다
  │
  └─ 미니게임이 뜨면 ─▶ 두드리기를 멈추고 겹칠 때만 누른다
                          │
                          └─▶ 빨간 글씨 = 낚았다 ─▶ 다시 던진다
```

정해진 순서대로 밀면 중간에 한 번 어긋난 뒤로 계속 어긋난다. 지금 화면이 어느
상태인지 보고 거기 맞는 것을 한다.

**미니게임 감지는 근거를 여럿 둔다** — 시간표시, 체력+막대, 막대+물고기. 하나만
서도 떠 있는 것으로 본다. 예전에는 시간표시를 정해 두면 그것 하나만 봤는데, 실제로
`time_min_px = 4006`이 저장돼 있었다. 그 영역은 88×38 = 3344칸뿐이라 **넘을 수 없는
문턱**이었고, 미니게임이 영원히 인식되지 않아 두드리기만 하고 있었다. 문턱이 영역의
칸 수를 넘으면 불러올 때 고쳐 주고, 처음 정할 때도 판 전체가 아니라 **잡은 영역
안에서** 센다.

돌아가는 동안 **상태가 바뀔 때마다 로그를 남긴다.** 시작할 때는 무엇을 어디서 보기로
했는지 전부 적는다 — 낚시가 안 돌 때 왜 안 도는지 알 길이 없는 것이 가장 답답하다.
같은 상태가 이어질 때는 5초에 한 번씩만 근황을 남긴다. 매 바퀴 찍으면 초당 백 줄이
쏟아져 로그가 쓸모없어지고, 그 줄을 만드는 비용이 그대로 클릭 수를 깎는다.

`fishing.py`는 화면도 입력도 모르는 순수 모듈이다. 그래야 가상 시계로 수백 판을 돌려
명중률을 잴 수 있다. 진짜 화면과 마우스에 잇는 일은 `fishtask.py`가 한다.

### 보관함
만들어 둔 매크로를 **폴더에 정리해서 보관**하고 나중에 다시 꺼내 쓴다.

작업 목록(`data/profile.json`)은 "지금 켜져 있고 핫키가 걸린 것들"이다. 반면
보관함은 항목 하나당 파일 하나로 저장한다. 탐색기에서 옮기고 복사하고 백업하기
쉽고, 파일 하나가 깨져도 나머지는 멀쩡하다.

```
<보관 폴더>/
    농사/
        기본 연타.z9m.json
        작물 감지.z9m.json
    목장/
        여물주기.z9m.json
```

- **폴더 변경** — 원하는 위치를 지정 (기본값은 프로젝트 안 `library/`)
- **새 카테고리** — 하위 폴더가 곧 카테고리
- **선택 항목 저장 / 작업 목록 전체 저장**
- **작업 목록으로 불러오기** — 항목을 더블클릭해도 된다
- **이름 변경 / 삭제** — 파일명과 항목 이름을 함께 바꾼다

불러올 때 이름이 겹치면 덮어쓰지 않고 새 이름을 붙인다. 실행 중인 항목을 몰래
바꿔 버리면 사용자가 이유를 알 수 없기 때문이다. 핫키도 가져오지 않는다 —
기존 항목과 충돌하면 둘 다 오작동한다.

### 설정
권한 진단, 대상 창 지정, 안전장치, 자동 교정, 전역 핫키, 화면 배율.

**자동 교정** — 몇 시간씩 돌리면 처음 설정한 것과 실제 상태가 조금씩 벌어진다.
벌어지는 곳은 늘 정해져 있어서, 시나리오의 **사이클과 사이클 사이**(입력이 하나도
안 나가 있는 유일하게 안전한 순간)에 세 가지를 되돌린다.

| 되돌리는 것 | 왜 |
|---|---|
| 창을 되찾느라 멈췄던 시간을 털고 시각 기준을 다시 잡는다 | 안 털면 바퀴마다 그만큼 죽은 시간이 새로 생긴다 |
| 눌린 채 남아 있는 키·버튼을 뗀다 | 키 뗌을 한 번 놓치면 그 뒤 입력이 전부 어긋난다 |
| 게임 창 크기가 달라졌으면 알린다 | 녹화해 둔 좌표가 그대로 빗나간다 |

기본은 **매 사이클**이고, 몇 사이클마다 할지 정하거나 아예 끌 수 있다. 무언가
실제로 고쳤을 때만 로그에 남으므로 평소에는 조용하다.

**화면** 칸에서 글씨·행 높이 배율을 100 ~ 200 %로 고를 수 있다. 고르면 그 자리에서
반영되고 바로 저장된다 (목록 열 너비처럼 몇 가지는 다시 시작해야 완전히 맞춰진다).
[창 크기 · 분할 초기화]는 끌어서 맞춰 둔 창 크기와 분할선을 화면 크기에 맞는
기본값으로 되돌린다.

## 정확도를 위해 이렇게 만들었다

측정값은 이 저장소에서 실측한 결과다.

**키는 스캔코드로 보낸다.**
Z9는 횡스크롤 MMORPG로 키보드 조작 위주이고, 클라이언트가 오래됐다. 이런 게임은
가상키 이벤트를 무시하고 스캔코드만 읽는 경우가 많다. `KEYEVENTF_SCANCODE`로
보내되, **keyup에도 같은 플래그를 유지한다** — 빼먹으면 게임이 키가 계속 눌린
것으로 인식하는 '키 고착'이 생긴다.

**절대 시각으로 스케줄링한다.**
"직전 이벤트와의 간격만큼 sleep"하면 sleep 오차가 매번 쌓여 30초짜리 매크로가
32초가 된다. 시작 시각 기준으로 각 이벤트의 목표 시각을 계산하고 그 시각까지
기다린다.

> 실측: 1.5초 구간 6개 이벤트의 스케줄 오차 최대 **0.40ms**, 누적 드리프트 없음.
> 연타 간격 50/100/200ms에서 평균 오차 **0.02ms**, 표준편차 **0.22ms**.
> 600바퀴를 이어 돌렸을 때 평균 오차 **0.33ms**, 앞 절반과 뒤 절반이 같다.

**멈췄던 시간은 그 회차에서 끝난다.**
게임 창이 뒤로 밀리면 되찾을 때까지 멈춰 선다. 그동안 밀린 만큼은 **그 회차의 남은
이벤트**를 뒤로 밀어 준다 — 안 그러면 되찾는 순간 밀린 입력이 한꺼번에 쏟아진다.

여기서 중요한 것은 **다음 회차로 넘어갈 때 그 몫을 털어야 한다**는 점이다. 회차마다
시각 기준을 새로 잡는데 밀림만 옛것으로 남으면, 새 기준에 옛 밀림이 계속 더해져
바퀴마다 죽은 시간이 새로 생긴다. 몇 시간 돌리는 동안 창이 몇 번만 밀려도 이렇게
벌어진다.

> 실측 — 0.05초짜리 매크로 3바퀴 (정상이면 3바퀴째가 0.10초에 시작):
>
> | 창을 2초 되찾은 적 | 바퀴별 첫 입력 시각 |
> |---|---|
> | 털지 않으면 | 2.00s · 4.05s · **6.10s** — 바퀴마다 2초씩 늘어난다 |
> | 털면 | 0.00s · 0.05s · **0.10s** |

**스핀 대기(busy-wait)를 쓰지 않는다.**
파이썬 스핀 루프는 GIL을 붙잡아 전역 훅 콜백 스레드를 굶긴다. Windows는 제한
시간 안에 응답하지 않는 저수준 훅을 통보 없이 제거하는데, 그러면 **비상 정지
핫키가 조용히 죽는다.** 대신 잘게 나눠 자되 남은 시간은 매번 절대 종료 시각에서
다시 계산해 오차가 누적되지 않게 했다. 정지 응답 지연은 5~8ms.

**훅은 스스로 복구한다.**
그럼에도 Windows가 훅을 떼어갈 수 있으므로 1초마다 다시 건다. 떼기에 실패하면
= 이미 시스템이 제거한 상태였다는 뜻이라, 그때만 로그에 남긴다.

**마우스 이동은 필요할 때만 훅에서 처리한다.**
이동 이벤트는 초당 수백 건씩 들어온다. 전부 파이썬으로 끌어올리면 훅 스레드가
밀려 위 문제를 자초한다. 녹화 중에만 켠다.

**픽셀은 영역을 한 번에 떠서 읽는다.**
화면 읽기 1회의 고정 비용이 픽셀 수보다 훨씬 크다(크기와 무관하게 약 6ms).
점을 따로 읽으면 3개에 18ms, 감싸는 사각형을 한 번에 뜨면 6ms로 **3배 빠르다.**
게다가 모든 점이 같은 프레임에서 나오므로 판정이 흔들리지 않는다. 점들이 화면
양 끝에 흩어져 영역이 너무 커질 때만 나눠 읽는다.

**감지 점은 여러 개 쓰는 게 좋다.**
한 점만 보면 애니메이션이나 파티클 한 프레임에 오탐이 난다. 2~4점을 AND로 묶으면
오탐이 급격히 줄어든다.

**모든 마우스 좌표는 게임 창 기준이다.**
화면 절대좌표로 저장하면 창을 조금만 옮겨도 어긋난다. 그래서 녹화·관찰·재생
어느 단계에서도 **그때그때 창 위치를 다시 읽어** 변환한다. 기준점을 한 번 잡아
캐시하면 그사이 창을 옮겼을 때 입력이 엉뚱한 곳으로 간다.

- 녹화 중에 창을 옮겨도 좌표가 어긋나지 않는다
- 녹화한 뒤 창을 옮기고 실행해도 같은 지점을 누른다
- 창 크기가 바뀌면 비례 보정 (옵션)
- 직접 빼지 않고 `ClientToScreen` / `ScreenToClient`를 쓴다 — DPI 가상화나 RTL
  레이아웃까지 OS가 처리해 준다
- DPI 인식(per-monitor v2)을 켜지 않으면 배율이 100%가 아닐 때 좌표가 통째로 틀어진다

> 검증: 창을 (450, 280)만큼 옮긴 뒤 같은 클라이언트 좌표를 해석했더니 화면 좌표가
> 정확히 같은 만큼 따라왔다. 창 크기를 400x300 → 800x600으로 키웠을 때 비례 보정도
> 정확했다.

게임 창을 못 찾은 채로 녹화하면 화면 절대좌표로 저장될 수밖에 없다. 이 경우
목록에 `⚠ 화면 절대좌표`로 표시되고, 실행할 때도 경고가 뜬다. `창 기준 좌표로
변환` 버튼으로 복구할 수 있다 (창이 녹화 때와 같은 위치에 있을 때 눌러야 한다).

**낚시는 시간이 아니라 화면으로 판단해야 한다.**
입질 타이밍은 매번 달라서 고정 주기로는 계속 놓친다. 픽셀 감지 주기를 60ms로
촘촘히 두는 편이 정확하다.

## 잘 안 될 때

| 증상 | 원인 |
|---|---|
| 매크로를 켰는데 게임에서 아무 반응이 없다 | 권한 부족. `관리자로 실행.bat` 사용. `설정` 탭 → `입력 전달 테스트`로 확인 |
| 엉뚱한 창에 입력이 들어간다 | 창 제목 패턴이 너무 느슨하다. `설정` 탭에서 창 목록을 보고 `선택한 창으로 고정` |
| 픽셀 캡처가 검은 화면으로 나온다 | 게임이 전체화면(독점) 모드. 창 모드로 변경 |
| 캐릭터가 계속 한 방향으로 간다 | 키가 눌린 채 끝났다. `F12`(비상 정지)로 강제 해제 |
| 핫키가 갑자기 안 먹는다 | 훅이 제거된 경우. 1초 내 자동 재설치되며 로그에 남는다 |
| 좌표가 어긋난다 | 목록에 `⚠ 화면 절대좌표`로 표시되는지 확인. 그렇다면 `창 기준 좌표로 변환`. 아니라면 창 크기가 바뀐 것이므로 `창 크기 변화 시 좌표 비례 보정`을 켤 것 |
| 보관한 매크로가 안 보인다 | `보관함` 탭에서 폴더 경로를 확인하고 `새로고침`. 파일이 깨졌으면 목록에서 조용히 빠진다 |

## 화면

원색을 쓰지 않는다. 매크로를 돌리는 동안 옆에 계속 띄워 두는 창이라 눈이 피로하면
안 되고, 강한 색은 정말 중요한 것에만 남겨 둬야 구분이 된다. 색은 역할로만 쓴다.

| 색 | 쓰이는 곳 |
|---|---|
| 무채색 | 대부분의 버튼 |
| 청회색 | 그 화면의 주된 동작 하나 (▶ 실행) |
| 벽돌색 | 되돌릴 수 없는 것 (삭제, 비상 정지) |
| 초록 / 호박색 | 상태 표시 (권한 정상 / 경고) |

이벤트 목록은 줄무늬를 넣어 행을 눈으로 따라가기 쉽게 했고, 끌어놓는 동안 놓을
자리는 옅은 청회색으로 표시된다.

### 창 크기와 분할선

창은 고정 크기가 아니라 화면 크기에 맞춰 열린다 (최대 1600x1060, 화면의 86 % 이내).
안쪽은 세 군데가 옅은 회색 선으로 나뉘어 있고, 그 선을 끌어 비율을 바꿀 수 있다.

| 분할선 | 나누는 것 |
